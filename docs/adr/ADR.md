## ADR-001: ターゲットプラットフォームを Pebble Emery に限定する

- **日付**: 2026-06-14（コミット履歴より再構成）
- **状態**: 採用
- **決定**: `appinfo.json` の `targetPlatforms` を `["emery"]` のみとする。
- **理由**: Emery はマイクを搭載した Pebble 最上位機種であり、Dictation API を使う本アプリには必須。他機種では `PBL_MICROPHONE` が未定義となり音声入力が動作しない。
- **トレードオフ**: Pebble Time 等の旧機種ユーザーは対象外になる。

## ADR-003: コンパニオン JS を ES5 で記述する

- **日付**: 2026-06-14（コミット `7469b26` より）
- **状態**: 採用
- **決定**: `src/pkjs/index.js` は ES5 構文のみ使用。アロー関数・`const`/`let`・`Array.prototype.findIndex` 等は不使用。
- **理由**: PebbleKit JS ランタイムは ES5 準拠であり、ES6+ 構文は実行時エラーになる。
- **トレードオフ**: コードが冗長になる（`firstNonSystemIndex()` 等の手動実装が必要）。

## ADR-004: AppMessage バッファサイズを 512 bytes に設定する

- **日付**: 2026-06-14（コミット履歴より再構成）
- **状態**: 採用
- **決定**: `app_message_open` の inbox/outbox サイズを `min(platform_max, 512)` とする。
- **理由**: Pebble のプラットフォーム上限が小さい環境でもクラッシュしないよう上限チェックを入れつつ、実用的なテキスト長を確保するために 512 bytes を選択。
- **トレードオフ**: 長い応答は JS 側で 500 文字にトリムされる（`text.substring(0, 500)`）。

## ADR-005: ウォッチ側履歴をリングバッファ 5 件とする

- **日付**: 2026-06-14（コミット `e36353f` より）
- **状態**: 採用
- **決定**: C 側の `HistEntry s_hist[5]` でウォッチ画面内の閲覧履歴を管理する。JS 側の会話コンテキスト（10 ターン）とは独立して管理する。
- **理由**: ウォッチのメモリ制約上、無制限に履歴を保持できない。Q: 128 B + A: 512 B = 640 B × 5 = 3.2 KB が現実的な上限。
- **トレードオフ**: ウォッチで閲覧できる過去 Q&A は最大 5 件のみ。JS 側の会話コンテキスト（10 ターン）より少ない。

## ADR-006: OpenAI モデルとして gpt-4o-mini を採用する

- **日付**: 2026-06-14（コミット履歴より再構成）
- **状態**: 採用
- **決定**: API リクエストのモデルを `gpt-4o-mini` に固定する。`max_tokens: 200`。
- **理由**: スマートウォッチの小画面では長文応答は不要。`gpt-4o-mini` は低レイテンシかつ低コストであり、腕時計の UX に適する。

## ADR-007: API キーの永続化に localStorage を使用する

- **日付**: 2026-06-14（コミット `5f639a7` より）
- **状態**: 採用（`5f639a7` で競合する保存場所を localStorage に一本化）
- **決定**: PebbleKit JS の `localStorage.setItem('openai_api_key', key)` のみを正とし、他の保存手段（`Pebble.getLocalStorageItem` 等）は使わない。
- **理由**: PebbleKit JS の `Pebble.getLocalStorageItem` と `localStorage` が別ストレージであることによる二重管理バグを解消するため。
- **トレードオフ**: `HARDCODED_API_KEY` 変数は開発テスト用にのみ残す（本番では空文字）。

## ADR-009: 設定 UI を GitHub Pages でホストする

- **日付**: 2026-06-14（コミット履歴より再構成）
- **状態**: 採用
- **決定**: `config/index.html` を `https://kukai.github.io/pebble-wrist-agent/config/` で公開する。JS 側はこの URL を `?v=N` のキャッシュバスト付きでオープンする。
- **理由**: Pebble の `showConfiguration` はリモート URL を必要とし、アプリバンドル内の HTML を直接参照できない。GitHub Pages は無料かつ静的ファイルのホスティングに適する。
- **トレードオフ**: 設定 UI の更新はリポジトリへの push が必要。スマートフォンのキャッシュ対策として `?v=N` を手動インクリメントする運用が必要。

## ADR-011: CONFIRM 画面を廃止して音声認識後に即送信する

- **日付**: 2026-06-21
- **状態**: 採用
- **決定**: 音声認識成功時に CONFIRM 画面を経由せず、`send_query()` を直接呼び出す。`SCREEN_CONFIRM` および関連 UI・クリックハンドラをすべて削除。
- **理由**: LLM は多少の音声認識誤りを文脈から補完できるため、送信前確認の価値が低い。ステップ削減（ボタン2回→1回）による UX 改善を優先。
- **トレードオフ**: 誤認識テキストを確認・キャンセルする手段がなくなる。誤認識時は ANSWER 画面から HOME に戻って再質問する運用で対応。

## ADR-012: PR #3 後の「STT→AI リクエスト消失」の原因は UUID 変更による API キー消失（コード変更なし）

- **日付**: 2026-07-08
- **状態**: 採用（インシデント記録。ADR-011 の即時送信方式は実機検証済みとして維持）
- **事象**: PR #3 適用後、音声認識は成功するのに AI への問い合わせが行われなくなった。当初は dictation コールバック内からの即時 `send_query()` が音声セッション解体と競合する仮説（遅延送信 + ウォッチ側リトライで対処）を立てたが、実機での切り分けの結果、原因は API キーの消失（JS が `error:no_api_key` を返す経路）と確認された。即時送信自体は問題なく動作している。
- **原因**: PR #3 で `appinfo.json` の UUID をプレースホルダから CloudPebble の UUID に変更した。PebbleKit JS の localStorage はアプリ UUID ごとに分離されるため、旧 UUID 時代に保存した `openai_api_key` が参照できなくなった。スマホアプリの設定画面にはキーが保存済みのように見えていたが、これは表示キャッシュであり実体は失われていた。
- **決定**: ウォッチ側コードは変更しない（遅延送信・リトライは実機で不要と確認されたため導入を撤回）。UUID 変更を伴うリリース時は、設定 UI から API キーを再入力する運用とし、CLAUDE.md / SPECS.md に注意事項として明記する。
- **教訓**: 認識成功後にフローが止まった場合、`pebble logs` で `[WA] handleQuery` の有無を確認すれば「ウォッチ→スマホ送信の問題」か「API キー/OpenAI 側の問題」かを即座に切り分けられる。

## ADR-013: 天気ツール（function calling）を Open-Meteo で実装する

- **日付**: 2026-07-09
- **状態**: 採用
- **決定**: OpenAI function calling で `get_weather(location?, date?)` ツールを追加する。天気データは Open-Meteo（Geocoding API + Forecast API）を使用し、場所未指定時は `navigator.geolocation` の現在地を使う（appinfo の `capabilities` に `location` を追加）。ツール実行 → 再問い合わせは最大 2 ラウンドに制限。tool 往復メッセージ（assistant の `tool_calls` / role=`tool`）は会話履歴に永続化せず、履歴には user と最終 assistant 応答のみ保存する。system プロンプトには毎リクエスト今日の日付を注入する（「明日」「週末」等の相対日付を LLM が解決するため）。
- **理由**: Open-Meteo は API キー不要のため、既存の OpenAI キー以外に秘密情報の管理を増やさない（設定 UI の変更も不要）。tool メッセージを履歴に残すと `MAX_HISTORY` トリムで assistant(`tool_calls`)/tool のペアが分断され OpenAI API がリクエストを拒否するため、永続化しない設計とした。
- **トレードオフ**: ツール利用時はレイテンシが増える（OpenAI → 位置解決 → 天気 API → OpenAI。各段にタイムアウトあり、最悪 ~50 秒）。商用天気 API と比べ地点精度・詳細度は限定的。ツール定義の分だけ毎リクエストの入力トークンが増える。
- **補足**: タイマーツールは未実装。実現にはウォッチ側の Wakeup API 対応（新 AppMessage キー、C 側のタイマー管理・通知 UI）が必要なため、別 ADR として検討する。

## ADR-014: ホーム画面を MenuLayer ベースの 3 セクションダッシュボードに再設計する

- **日付**: 2026-07-18
- **状態**: 採用
- **決定**: アプリ起動直後の HOME を、単一の音声入力画面から MenuLayer の 3 セクション構成に変更する。S1 = 「話す」（固定 1 行・常に初期選択）、S2 = アクティブなタイマー/ストップウォッチ一覧（0 件時は非表示）、S3 = 固定メニューテーブル（現在は「会話履歴」のみ。`s_fixed_items[]` 配列への追記だけで行を拡張できる）。S2 の行操作は Pebble 標準の ActionMenu API を使い、独自サブメニューは実装しない。S2 の時間表示はカウンタを持たず、TickTimerService（SECOND_UNIT・HOME 表示中のみ購読）で `layer_mark_dirty` し描画時にタイムスタンプ差分から再計算する。
- **理由**: Pebble Time 2 のクイックローンチ枠が既に埋まっており、タイマー等の新機能は WristAgent 内に統合する必要がある。MenuLayer 化により将来の項目追加（天気/メモ/Home Assistant）に行数決め打ちなしで耐えられる。HOME 表示のたびに「話す」を初期選択に戻すことで、従来の「起動して Select 即発話」の体感を維持する。
- **トレードオフ**: UP/DOWN がメニュー移動に割り当てられるため、従来の「HOME UP 長押しで会話リセット」は廃止。代替として S3 に「会話履歴」項目を設け、リセットは ANSWER（履歴）画面の SELECT 長押し (700 ms) に移設した（ユーザー確認済み）。旧 HOME の履歴カウンタ表示（"[履歴: N件]"）は廃止。
- **補足**: 要件上の「🎤」絵文字は Pebble システムフォントで描画できないため、行タイトルはテキスト「話す」とした。

## ADR-015: タイマー/ストップウォッチを Wakeup + PersistentStorage + function calling で統合する

- **日付**: 2026-07-18
- **状態**: 採用
- **決定**:
  - OpenAI function calling に `set_timer(duration_seconds, label?)` / `start_stopwatch(label?)` を追加。JS はツール実行時に新 AppMessage キー（`KEY_TIMER_SET`=4, `KEY_TIMER_LABEL`=5, `KEY_STOPWATCH_START`=6）でウォッチへ送信し、**ウォッチの ack を待たず楽観的に tool 結果を即時返却**する（レイテンシ最小化。予約失敗はウォッチ側ステータス表示で通知）。
  - ウォッチ側は固定長 4 スロットでタイマー/SW を管理し、PersistentStorage（キー 100+n）に構造体ごと永続化。タイマーは Wakeup API（cookie=スロット番号, notify_if_missed=true）で満了通知し、予約が排他ウィンドウ等で失敗した場合は 5 秒ずらして最大 8 回リトライする（Pomodoro で確認済みの制約への対応）。最短 30 秒未満の指定は 30 秒に切り上げ。満了時はバイブ + スロット削除。
  - タイマー/SW を音声セットした直後の LLM 応答（KEY_RESPONSE）受信時は、ANSWER でなく HOME に戻る（`s_pending_home` フラグ）。応答自体は履歴に保存され後から閲覧できる（ユーザー確認済み。ストップウォッチは要件どおり、タイマーも同挙動に統一）。
  - ActionMenu 経由の操作（一時停止/再開/リセット/削除、SW の Start/Stop/Lap/Reset）はすべてローカル処理で完結し、LLM 往復を挟まない。タイマー一時停止は Wakeup キャンセル + 残り秒保存、再開は再スケジュール。
  - 起動時に実行中タイマーの `wakeup_query` を検証し、発火済みなら削除、予約消失なら残り時間で再スケジュールするサニタイズを行う。
- **理由**: ストップウォッチの Start/Stop/Lap は LLM 往復のレイテンシに耐えられないため、開始トリガーのみ音声・操作はローカルというハイブリッド設計とした。tool 結果の楽観的返却は、AppMessage の ack 待ち（NACK リトライ込みで最悪数秒）が LLM の第 2 ラウンドを遅らせるのを避けるため。tool 往復を履歴に永続化しない方針は ADR-013 を踏襲。
- **トレードオフ**: スロット満杯・Wakeup 予約失敗が LLM に伝わらないため、応答文（「セットしました」）と実際の状態が食い違う可能性がある（ウォッチのステータス行表示で補完）。Wakeup は 1 アプリ最大 8 件だが、スロット上限 4 のため実用上問題ない。スロット構造体の Persist 書き込みはスロット単位（≤ 256 B/キー制限内）。

## ADR-016: HOME の BACK ボタンを明示的にサブスクライブする

- **日付**: 2026-07-19
- **状態**: 採用
- **事象**: PR #5（ADR-014）適用後、実機（Pebble Time 2）で複数回「Listening→発話→送信」サイクルを繰り返すと、HOME 画面で BACK ボタンの短押しが反応しなくなるタイミングが報告された。その状態で BACK を長押しすると、Pebble OS のシステム仕様により強制的にアプリが終了しランチャーへ戻る（これはアプリコードで変更不可能な OS 標準動作であり、それ自体はバグではない）。
- **調査**: `menu_layer_set_click_config_onto_window()` は UP/DOWN（スクロール）と SELECT のみをバインドし、BACK は明示的に触れない。公式ドキュメント（[Clicks - Pebble Developers](https://developer.rebble.io/docs/c/User_Interface/Clicks/)）によれば、BACK は何もバインドしなければデフォルトで「ウィンドウを閉じる」動作にフォールバックするはずであり、通常は MenuLayer 使用時でも問題なく動作する。ただし実機での再現性・タイミング依存の性質から、暗黙のデフォルト挙動への依存を排除する方が安全と判断した。
- **決定**: HOME の Click Config Provider を `menu_layer_set_click_config_onto_window()` に一任せず、一度だけ `window_get_click_config_provider()` でその関数を保存し、`home_click_config_provider()` でラップして呼び出したうえで BACK を明示的に `window_single_click_subscribe()` する（[Pebble: How to override the back button when you are using a menu layer](https://gist.github.com/sarfata/10574031) の定石パターンを踏襲）。あわせて LOADING 画面も BACK を明示的に no-op へバインドし、リクエスト中に BACK でアプリが終了できてしまう抜け道（「操作無効」の仕様に反する）を塞いだ。
- **トレードオフ**: なし。既存の「BACK でアプリ終了」という挙動自体は変えておらず、暗黙のデフォルトに依存していた部分を明示化しただけ。根本原因（BACK が時々反応しなくなる具体的なメカニズム）は実機ログでの追加検証なしには完全には特定できていないため、再発した場合は `pebble logs` でクリックイベントの受信有無を確認すること。

## ADR-017: タイマー/ストップウォッチを HOME の常設メニュー（S3）からも追加できるようにする

- **日付**: 2026-07-19
- **状態**: 採用
- **決定**: HOME S3 に「タイマー」「ストップウォッチ」の固定項目を追加する。「タイマー」選択時、アクティブなタイマーが 1 件もなければタイマー設定画面（ActionMenu によるプリセット選択: 1/3/5/10/15/20/30分）へ自動遷移し、既にあれば該当タイマーの既存 ActionMenu（S2 行選択時と同じ）を開く。「ストップウォッチ」も同様の構造だが、未設定時はプリセット不要のためボタン操作のみで即座に開始する。既存タイマー/SW の ActionMenu にも、空きスロットがある場合に限り「新しいタイマー」/「新しいストップウォッチ」項目を追加し、既に1件動いていても追加できるようにする。
- **理由**: 音声を使わずボタン操作だけでタイマー/SW を開始・追加できる導線を求められたため。時間指定は Pebble 標準 API に数値入力ウィジェットが無く、既に実績のある ActionMenu を再利用する方が実装・検証コストが低いためプリセット選択方式とした（NumberWindow 相当の自作 UI は今回見送り）。プリセット選択・新規追加とも、音声経由の `set_timer`/`start_stopwatch` と同じ `handle_timer_set()`/`handle_stopwatch_start()` を再利用し、ロジックの二重管理を避けている。
- **トレードオフ**: 複数のタイマーが同時にアクティブな場合、S3「タイマー」は先頭の 1 件の ActionMenu しか開かない（2 件目以降は S2 から個別に操作する必要がある）。プリセット以外の任意の時間（例: 7分）はボタン操作のみでは指定できず、音声か最寄りのプリセットで代替する必要がある。

## ADR-018: 会話履歴をユーザーがリセットするまで PersistentStorage に永続化する

- **日付**: 2026-07-19
- **状態**: 採用
- **事象**: アプリを再起動すると会話履歴（ANSWER 画面で閲覧する Q&A）が消えるという報告があったが、調査の結果これは PR #5 による regression ではなく、`s_hist` リングバッファは元々一貫してメモリ上にのみ保持されており、永続化の実装自体がこれまで存在しなかったことが判明した（ADR-005 は表示件数の上限を定めたのみで、永続化の可否には触れていない）。
- **決定**: `s_hist`（`HistEntry s_hist[HIST_CAP]`）を PersistentStorage に永続化する。1 キー最大 256 bytes の制約があるため、各エントリの `q`（128 bytes）は 1 キー、`a`（512 bytes）は 256 bytes ずつ 2 キーに分割して保存し、件数は別途メタキーに保存する。`push_history()` のたびに全件を書き直し、`reset` コマンド（ウォッチ側 SELECT 長押し、または JS 側 `reset_ok`）で全キーを削除する。件数の上限は ADR-005 で決定済みの `HIST_CAP = 5` をそのまま踏襲し、変更しない。
- **理由**: 「ユーザーがリセットするまで履歴は保持されてよい」という要望と、既にタイマー/SW スロットで確立している PersistentStorage 永続化のパターンを踏襲するのが自然だったため。件数上限を変える意思決定は特になされていないため、既存の ADR-005 の方針（メモリ制約に基づく 5 件）をそのまま流用した。
- **トレードオフ**: `push_history()` のたびに複数キーへの書き込みが発生し、Wakeup サニタイズ等と合わせてフラッシュ書き込み頻度がやや増える（実用上は許容範囲）。JS 側の `conversationHistory`（会話コンテキスト、最大 10 ターン）は今回の対応範囲外であり、引き続きアプリ再起動で失われる（ウォッチ側の閲覧履歴とスマホ側の LLM コンテキストは ADR-005 のとおり独立管理のため）。

## ADR-021: HOME を単一セクション・固定行リストに再設計する（ADR-014 の S1/S2/S3 構成、ADR-017/ADR-020 の S2 挙動を上書き）

- **日付**: 2026-07-19
- **状態**: 採用（ADR-014 で決定した「S2 はアクティブなインスタンス数だけ行が増減する動的リスト」という設計を撤回し、本エントリの方針に置き換える）
- **事象**: ADR-020 で「タイマー/SW を新規作成した直後は ActionMenu を自動的に開く」対応を行ったところ、フィードバックとして「S2 から選び直す手間をなくすことが本質ではなく、S2 のメニューがタイマー・ストップウォッチの状態ごとに増える実装自体をやめてほしい」という指摘を受けた。さらに、「タイマー」「ストップウォッチ」は S2 のインスタンスとして表現されるべきだが、動的にではなく S3 の項目のように**常に存在する固定行**として、かつ「話す」「会話履歴」と同列に並ぶものとして扱いたい、という方針が示された。
- **決定**: HOME の MenuLayer を、旧来の S1（話す）/S2（動的なタイマー・SW 一覧）/S3（固定メニュー）という 3 セクション構成から、**単一セクション・固定 5 行**（`s_home_rows[]`: 話す・タイマー・ストップウォッチ・会話履歴・天気）に作り直す。
  - 「タイマー」「ストップウォッチ」の行自体はインスタンスの有無・数にかかわらず常に1行のまま存在する（行の増減をやめる）。
  - 各行の状態は行タイトルではなくサブタイトルで表現する: 未設定時は「未設定」、アクティブなら最初に見つかったスロットの残り/経過時間（+ ラベルがあれば付記）。複数同時にアクティブな場合は "+N件" を付記して存在だけは示すが、2件目以降の個別操作は行選択後の ActionMenu（3.4）経由に限定する。
  - 旧 `active_slot_count()`/`active_slot_index()`（S2 の動的行数計算用）は不要になったため削除。`SECTION_TALK`/`SECTION_ACTIVE`/`SECTION_MENU`/`NUM_SECTIONS`/`FixedMenuItem`/`s_fixed_items[]` も同様に廃止し、`MenuRow`（title・callback・subtitle 関数の3つ組）による統一テーブルに置き換えた。
  - 「タイマー」「ストップウォッチ」行の選択挙動（未設定なら作成へ、設定済みなら ActionMenu へ）自体は ADR-017/ADR-020 の内容を踏襲し、変更しない。
- **理由**: タイマー/ストップウォッチという「機能への入口」は、話す・会話履歴と同じ性質の固定的なメニュー項目であり、たまたまバックエンドで複数インスタンスを保持できる（SLOT_COUNT=4）としても、それがホーム画面のレイアウトを動的に変化させる理由にはならない、という設計判断。行数が固定であることにより、UP/DOWN でのメニュー操作の感覚が常に一定に保たれる。
- **トレードオフ**: 複数のタイマー/SW が同時にアクティブな場合、HOME 画面からは「+N件」としてしか件数がわからず、2件目以降の詳細（残り時間やラベル）を見るには一度 ActionMenu を開く必要がある（ADR-014 時点の「一覧性」は後退する）。バックエンドのスロット数上限（4件）や PersistentStorage 設計（ADR-015）自体には変更なし。
- **補足**: この「2件目以降が HOME から見えない」というトレードオフは、直後の ADR-022 でタイマー・SW を各1件までに制限したことで実質的に解消された（そもそも2件目が存在しなくなるため）。

## ADR-022: HOME メニューの並び替え・天気アイコン・循環スクロール・タイマー/SW を1件までに制限

- **日付**: 2026-07-19
- **状態**: 採用（ADR-021 の「+N件」表記を前提としたトレードオフを解消する形で、タイマー/SW の同時保持数に関する方針を追加する）
- **事象**: ADR-021 の運用後、「複数のタイマー/ストップウォッチを設定できるが、2件目を確認できる場所がない」という指摘を受けた。あわせて、行の並び順（会話履歴は最下部が良い、天気は2番目が良い）、天気行をアイコンで表現できないか、メニューの UP/DOWN 操作を循環スクロールにしてほしい、という 4 点の要望があった。
- **決定**:
  1. **行の並び替え**: `s_home_rows[]` の並びを「話す・天気・タイマー・ストップウォッチ・会話履歴」に変更（天気を2番目、会話履歴を最下部へ）。
  2. **天気アイコン**: `resources/images/icon_weather.png`（25x25、透過PNG、太陽のグラフィック）を新規作成し `appinfo.json` の `resources.media` に `ICON_WEATHER` として登録。`window_load` で `gbitmap_create_with_resource(RESOURCE_ID_ICON_WEATHER)` により読み込み、`MenuRow` に `GBitmap **icon` フィールドを追加して「天気」行のみアイコン付きで描画する。`window_unload` で `gbitmap_destroy()`。
  3. **循環スクロール**: HOME の Click Config Provider に `home_up_click`/`home_down_click` を追加し、`menu_layer_get_selected_index()`/`menu_layer_set_selected_index()` を使って MenuLayer 既定の「端で止まる」UP/DOWN 挙動を上書き。先頭行で UP → 末尾行へ、末尾行で DOWN → 先頭行へ移動する。
  4. **タイマー/SW を1件までに制限**: `SLOT_COUNT` を 4 から **2**（タイマー用・SW用に1つずつ）に縮小し、`handle_timer_set()`/`handle_stopwatch_start()` の入口で「既に同じ種別のスロットが存在するか」をチェックして拒否するガードを追加。この関数はボタン操作・音声（LLM の `set_timer`/`start_stopwatch` 関数呼び出し）の両方から呼ばれるため、経路によらず一貫して 1 件までに制限される。ActionMenu の「新しいタイマー」/「新しいストップウォッチ」項目（ADR-017/ADR-020）は不要になったため削除し、`ACTION_MENU_CAPACITY` も 5 から 4 に縮小した。
- **理由**: 4 は UI 面の改善要望をそのまま反映。5-1（並び替え）・5-2（アイコン）・5-3（循環スクロール）は見た目・操作性の調整で、いずれも既存のデータモデルに影響しない。5-4（1件までに制限）は、ADR-021 で「複数アクティブでも HOME からは "+N件" としてしか分からない」というトレードオフとして許容していた問題に対する根本対応であり、HOME を固定行リストにした ADR-021 の設計（1行=1種別の状態表示）と最も自然に整合する解決策として、複数インスタンス機能自体を削るという判断をした。
- **トレードオフ**: 同時に複数の目的でタイマーを使う（例: 調理と洗濯を同時に計測する）ユースケースはサポートされなくなる。天気アイコンは実機での見た目を筆者（Claude）が確認できておらず、Pebble Emery（カラー）実機での表示確認が必要。SLOT_COUNT を縮小したことで PersistentStorage のスロットキー（`100`, `101`）以外への影響はない（キー番号自体は変更していないため、旧 4 スロット時代のデータが残っていても後方互換）。

## ADR-023: タイマー/ストップウォッチ/天気を専用のフルスクリーンビューにする（ActionMenu・プリセットピッカーを廃止）

- **日付**: 2026-07-27
- **状態**: 採用
- **事象**: HOME の5項目のうち「会話履歴」（ANSWER）だけが専用画面を持ち、
  「タイマー」「ストップウォッチ」は Pebble 標準 `ActionMenu`（モーダル選択
  リスト）で操作し、「天気」は音声質問と全く同じ経路（LOADING→ANSWER）を
  再利用するだけで専用画面を持たなかった。「会話履歴と同じように、他の
  項目も専用の独立したビューにしてほしい」という要望を受けた。あわせて、
  タイマーの時間設定もプリセット選択（ActionMenu で1/3/5/10/15/20/30分）
  から分・秒を刻んで指定できる専用ピッカーに変更したいという要望があった。
- **決定**:
  1. `Screen` enum に `SCREEN_WEATHER`・`SCREEN_SLOT`・`SCREEN_TIMER_SET` を
     追加する。いずれも新しい Pebble `Window` は増やさず、既存の単一
     `s_window` 内でレイヤーの表示/非表示と Click Config Provider を
     切り替える既存方式（HOME/LOADING/ANSWER と同じ）を踏襲する。
  2. **SCREEN_SLOT**（タイマー/ストップウォッチ共通の操作ビュー）:
     ActionMenu を廃止し、専用ビュー上でボタンに直接アクションを割り当てる。
     SELECT短押し=トグル（一時停止/再開 or 開始/停止）、SELECT長押し(700ms)
     =リセット、UP短押し=Lap（SWのみ）、BACK短押し=HOMEへ戻る、BACK長押し
     (700ms)=削除してHOMEへ。ActionMenu の各アクション本体（`am_timer_toggle`
     等）は `slot_toggle`/`slot_reset`/`slot_lap`/`slot_delete` として
     kind（タイマー/SW）で分岐する共通関数に統合し、タイマー/SW 用に
     コードを分けない。同期的な画面遷移になったため、旧 `did_close` 経由の
     遅延オープン（`s_open_slot_pending`）は不要になり削除した。
  3. **SCREEN_WEATHER**（天気専用ビュー）: 既存の ANSWER 表示レイヤー
     （タイトル+スクロール本文+下部ヒント）をそのまま流用し、内容だけ
     差し替える共通ヘルパー `set_answer_style_content()` を新設。天気は
     固定タイトル「天気」+ 応答本文のみを表示し、履歴前後移動・会話
     リセットの長押しはバインドしない（単発表示のため不要）。
     `menu_item_weather()` は `send_query()` 前に `s_pending_weather` フラグを
     立て、`inbox_received_handler` の応答受信時に
     `s_pending_home → HOME` / `s_pending_weather → SCREEN_WEATHER` /
     それ以外 `→ SCREEN_ANSWER` の3分岐にする。会話履歴への保存
     （`push_history()`）は分岐に関係なく従来通り行い、保存範囲は変更しない。
  4. **SCREEN_TIMER_SET**（分秒ピッカー）: ActionMenu によるプリセット選択
     （1/3/5/10/15/20/30分）を廃止し、分（0–180、循環）・秒（0–59、循環）
     を左右に表示する専用ビューに変更。UP/DOWN短押しで選択中フィールドを
     ±1、SELECT短押しで分⇄秒のフィールド切替、SELECT長押し(700ms)で
     `分*60+秒` を既存の `handle_timer_set()` にそのまま渡して決定、
     BACK短押しでキャンセルしてHOMEへ。`handle_timer_set()` 自体（30秒
     未満切り上げ・1件までのガード）は変更しない。
- **理由**: ActionMenu はモーダルオーバーレイであり「会話履歴のような
  独立したビュー」という要望の意図（画面全体を専用の見た目・操作系で
  占有する）に合わないため、既存の Screen 切り替え方式に統一した。
  ActionMenu のアクション本体ロジック自体は変更が不要だったため、
  ボタンハンドラから直接呼ぶ形に配線し直すだけで再利用した。天気は
  ANSWER と見た目の構造（スクロール可能テキスト）が同一のため、レイヤーを
  二重に持たず内容差し替えヘルパーで共有し、無用な重複を避けた。分秒
  ピッカーは、Pebble SDK 3 に数値入力ウィジェットが無いという ADR-017
  当時の制約は変わらないため、TextLayer 2枚 + 反転色によるフォーカス表現
  という最小構成の自作 UI で実現した。
- **トレードオフ**: SCREEN_SLOT の BACK 短押し/長押しという操作は、従来
  「BACKでActionMenuを閉じてHOMEへ」の感覚に「長押しで削除」という新しい
  ジェスチャーが加わっており、実機での誤操作（うっかり長押しして削除）の
  リスクは ActionMenu の個別「削除」項目選択より上がる可能性がある。分秒
  ピッカーは決定までに最大 2 プッシュ（フィールド切替+増減）を要し、
  よく使う時間（5分など）についてはプリセット方式より操作数が増える
  ケースがある。天気の応答は引き続き会話履歴にも保存されるため、
  「専用ビュー」であることと「会話履歴に残る」ことは両立しており矛盾しない。

## ADR-024: タイマー満了時、ユーザーが止めるまでバイブを繰り返す

- **日付**: 2026-07-27
- **状態**: 採用
- **事象**: `handle_timer_fired()` は満了時に `vibes_double_pulse()` を一度
  呼ぶだけで、あとはスロット削除＋ステータス行の文言更新のみだった。腕時計
  という性質上、一度のバイブでは気づかず見逃すという指摘を受けた。
- **決定**: タイマー満了時、専用の `SCREEN_ALARM` 画面へ強制的に遷移し
  （それまでどの画面を表示していたかに関わらず割り込む）、
  `vibes_double_pulse()` を `ALARM_VIBE_INTERVAL_MS`（2秒）間隔の
  `AppTimer`（`alarm_vibe_timer_cb`）で繰り返す。ユーザーが SCREEN_ALARM 上で
  SELECT/BACK/UP/DOWN いずれかのボタンを押すと `stop_alarm_vibration()` が
  `AppTimer` をキャンセルし、HOME へ戻る。該当スロットは（旧実装と同じく）
  満了と同時に削除し、ラベルだけ `s_alarm_label` に退避して SCREEN_ALARM の
  表示に使う。アプリ終了時（`deinit()`）にも念のため `stop_alarm_vibration()`
  を呼び、タイマーを残さない。
- **理由**: 単発のバイブでは睡眠中や作業中に見逃しやすく、「ユーザーが
  明示的に止めるまで鳴り続ける」という一般的なアラーム/タイマーアプリの
  挙動に合わせた。専用画面へ強制遷移する設計は、既存の Screen 切り替え
  方式（ADR-023）にそのまま乗せられ、新しい Window や特別な割り込み機構を
  必要としなかった。
- **トレードオフ**: タイマー満了時に他の操作（会話履歴の閲覧、天気の確認
  など）を中断させる強制遷移になるため、他の画面を操作中にタイマーが
  鳴ると、その場の状態（例: ANSWER のスクロール位置や SLOT の一時停止操作
  途中）は失われる。バイブを止めるまでの間、他の操作は一切できない
  （ワンボタンで即座に停止できるため実用上の支障は小さいと判断）。

- **事象**: ADR-023/ADR-024 で追加した専用ビューについて、実機/エミュレータ

     30px の間）の高さ `content_h` を基準に、SLOT の時間+サブテキスト
     ブロック、分秒ピッカーの数字行、ALARM のメッセージ層の Y 座標を
     `content_top + (content_h - ブロック高さ) / 2` で算出し、上下中央に
     揃える。
  2. `ALARM_VIBE_INTERVAL_MS` を 2000 → **1000**（1秒間隔）に短縮。
  3. 分秒ピッカーの分/コロン/秒の3レイヤーを、画面幅の半分ずつではなく
     数字2桁分の固定幅（各50px、コロン20px、合計120px）にまとめ、
     `(画面幅 - 120) / 2` を起点に画面中央へ配置。これに伴い分・秒レイヤーの
     文字寄せも右寄せ/左寄せから中央寄せに統一した。
- **理由**: レイアウト定数はマジックナンバーのまま `window_load()` 内に
  `const int` で留め、既存のヘッダー未追加の構成を維持しつつ最小限の
  修正で3点すべてに対応した（`#define` を関数内に書くとファイル全体に
  漏れるため、ローカル `const int` にした）。
- **トレードオフ**: なし。表示位置とタイミング定数の調整のみで、状態遷移や
  ボタン割り当てのロジックには影響しない。

## ADR-027: タイマー確定を確認ビュー化・秒を10秒刻みに・リセット自動再開の廃止・Lap履歴の追加

- **日付**: 2026-07-29
- **状態**: 採用
- **事象**: レビューで以下4点の指摘を受けた。
  1. タイマー設定の秒は1秒刻みでなく10秒刻みでよい。
  2. 分秒ピッカーの確定操作が SELECT 長押し（700ms）なのは直感に反する。
     確認用の専用ビューにすべき。
  3. SLOT のリセット（3.4）で、タイマーがリセット直後に自動的に再スタート
     してしまうのは望ましくない。
  4. ストップウォッチで複数回 Lap を記録できるのはよいが、記録した Lap を
     確認するビューがない（`last_lap` で直近1件しか見えない）。
- **決定**:
  1. `tset_up_click`/`tset_down_click` の秒フィールド増減を `TSET_SECOND_STEP`
     (10) 単位にする（`(s_ts_seconds + 10) % 60` / `(s_ts_seconds + 50) % 60`）。
  2. 分秒ピッカーの SELECT 短押しを「分→秒→確認画面」と前にしか進まない
     一方向の遷移に変更し、SELECT 長押しでの確定処理は廃止する。新設の
     `SCREEN_TIMER_CONFIRM` で `MM:SS` と確認メッセージを表示し、
     SELECT 短押しで確定（`handle_timer_set()` 実行）、BACK 短押しで
     分秒ピッカーの分編集に戻る（値は保持）。表示レイヤーは新規に増やさず
     SLOT（3.4）の `s_slot_title_layer`/`s_slot_time_layer`/`s_slot_sub_layer`/
     `s_slot_hint_layer` を再利用する（幅の狭い `s_tset_*` 側を流用すると
     ADR-026 と同じ省略記号の問題が再発するため）。
  3. `slot_reset()` のタイマー分岐から `schedule_timer_wakeup()` の再呼び出しを
     削除し、Wakeup キャンセル + `running=0` + `remaining=duration` の
     「停止状態に戻すだけ」に変更する。SW のリセットは既存どおり
     （停止・0秒・last_lap/lap_countクリア）で変更なし。
  4. `Slot` 構造体に `laps[MAX_LAPS=8]`（Lap秒の履歴）と `lap_count` を追加
     （既存フィールドの末尾に追加するためオフセットは変わらず、旧構造体で
     永続化されたデータとの互換は保たれる）。`slot_lap()` は `last_lap` に加え
     `laps[]` に追記し、上限超過時は会話履歴（`push_history()`）と同じ
     「最古を1件捨てて詰める」方式にする。新設の `SCREEN_LAPS` は
     ANSWER/WEATHER と共有のスクロール表示レイヤー
     （`set_answer_style_content()`）を再利用してLap一覧を表示する。
     SLOT のストップウォッチ画面で DOWN 短押し（従来未割当）から遷移し、
     BACK で SLOT へ戻る（HOMEではなく呼び出し元へ）。
- **理由**: いずれもレビューで指摘された実際の使い勝手の問題への対応。
  表示レイヤーの追加を避けて既存の共有レイヤーパターン（ADR-023）を
  踏襲することで、実装・保守コストを抑えた。Lap履歴の上限とあふれ処理は
  既存の会話履歴（HIST_CAP）と同じ考え方を流用し、新しい設計パターンを
  持ち込まないようにした。
- **トレードオフ**: 分秒ピッカーが前方向のみの遷移になったため、分を
  編集し終えたあとに気づいた分の間違いを直すには、確認画面まで進んで
  BACK で分編集からやり直す必要がある（従来の SELECT トグルによる
  即座の行き来はできない）。Lap履歴は最大8件までで、それを超えると
  古いLapから消える（無制限の記録はサポートしない）。

## ADR-028: タイマーのリセットで時間を設定し直せるようにする

- **日付**: 2026-07-29
- **状態**: 採用
- **事象**: ADR-027 でタイマーのリセットを「停止状態・元の長さに戻すだけ」
  に変更したが、レビューで「リセットしても時刻設定できません。前回設定
  した時刻にリセットされるだけです」という指摘を受けた。ユーザーは
  リセットの機会に新しい時間を設定し直したかったが、既存の実装では
  タイマーを削除して作り直す以外に長さを変更する手段がなかった。
- **決定**: SLOT（3.4）でタイマー表示中の SELECT 長押しを、即座のリセット
  処理ではなく **分秒ピッカー（SCREEN_TIMER_SET）をそのタイマーの現在の
  長さでプリセットして開く** 処理に変更する。
  - `slot_select_long_click` はタイマーの場合、`s_ts_minutes`/`s_ts_seconds`
    を `duration` から算出してセットし、`show_screen(SCREEN_TIMER_SET)`
    する（`s_open_slot` は編集対象のスロットを指したまま変更しない）。
  - `SCREEN_TIMER_CONFIRM` の決定処理（`tconfirm_select_click`）は
    `s_open_slot` が既存のタイマースロットを指しているかどうかで分岐する。
    指していれば「編集」とみなし、`handle_timer_set()`（1件までのガード
    付き）を経由せず直接そのスロットの `duration`/`remaining` を書き換えて
    停止状態にする。指していなければ従来どおり `handle_timer_set()` で
    新規作成する。
  - `menu_item_timer()` の新規作成分岐では `s_open_slot = -1` を明示し、
    直前の画面遷移で残った可能性のある古い値による誤判定を防ぐ。
  - `slot_reset()` はストップウォッチ専用の関数に縮小し（タイマー分岐を
    削除）、SLOT のヒント文言も「長:リセット」→「長:時間設定」に変更した。
- **理由**: 値を変えずに確認すれば結果的に「元の長さへのリセット」として
  機能するため、旧来の「リセット」の需要も損なわず、かつ新しい時間の
  設定という要望も同じ導線で満たせる。既存の分秒ピッカー→確認画面という
  UI（ADR-027）をそのまま流用でき、新しい画面や操作体系を増やさずに済んだ。
- **トレードオフ**: 「今すぐ元の長さに戻す」だけを目的とする場合でも、
  分秒ピッカー→確認画面という2ステップを経由する必要があり、ADR-027 の
  「SELECT長押し一発でリセット」より手数がわずかに増える。分秒ピッカーの
  BACK は常に HOME へ戻る（変更前のタイマーは編集されず残るため実害は
  ないが、SLOT 画面に直接戻りたい場合は再度「タイマー」を選択する必要が
  ある）。

## ADR-029: 分秒ピッカーで30秒未満を選べてしまう問題を修正

- **日付**: 2026-07-29
- **状態**: 採用
- **事象**: レビューで「10秒を設定しても30秒が設定される」という指摘を
  受けた。原因は `handle_timer_set()`（ADR-015 由来）が Wakeup API の
  制約（30秒未満は予約不可）に合わせて `duration` を `TIMER_MIN_SECONDS`
  (30) に黙って切り上げる仕様であるのに対し、分秒ピッカー（ADR-023/027）
  は分・秒を独立に0から選べてしまい、ユーザーが「0分10秒」のような
  30秒未満の組み合わせを選択できてしまうこと。選んだ値と実際に設定される
  値が食い違うにもかかわらず、確認画面にもその旨の表示がなかった。
- **決定**: `tset_up_click`/`tset_down_click` の末尾で新設の
  `tset_clamp_min_duration()` を呼び、**分が0のときは秒を30秒未満に
  できない**ようにする（分が0のときの秒の選択肢は 30/40/50 のみ。分を
  1以上に増やせば秒は0から選べる）。`handle_timer_set()` 側の30秒未満
  切り上げ処理自体は変更しない（音声経由の `set_timer` など、ピッカーを
  経由しない他の入力元に対する安全弁として引き続き機能させる）。
- **理由**: 実際に選択可能な値と、確定後に得られる結果を一致させることを
  優先した。確認画面に「30秒に切り上げられます」という注記を追加する案も
  検討したが、そもそも選べない方が誤解の余地がなくシンプルなため、ピッカー
  側で選択肢自体を制限する方式を採用した。
- **トレードオフ**: 分が0のときに秒を30秒刻み実質3択（30/40/50）まで
  絞り込むため、「0分5秒だけ待ちたい」といった短時間の指定はそもそも
  この画面からはできない（Wakeup API の制約上、実現不可能な値であるため
  妥当な制限と判断）。

## ADR-030: 分秒ピッカーの秒編集中に BACK で分編集へ戻れるようにする

- **日付**: 2026-07-29
- **状態**: 採用
- **事象**: ADR-027 で分秒ピッカーの SELECT 短押しを「分→秒→確認画面」の
  一方向遷移にした際、秒を編集中に分の値を直したくなった場合は確認画面
  まで進んで BACK で分編集に戻るしかなかった。レビューで「秒の設定時に
  分に戻りたい」という指摘を受けた。
- **決定**: `SCREEN_TIMER_SET` の BACK 短押し（`tset_back_click`）を
  編集中フィールドで分岐させる。秒編集中（`s_ts_field == 1`）は
  `s_ts_field = 0` にして分編集へ一段階戻るだけとし、`SCREEN_HOME` への
  遷移はしない。分編集中（`s_ts_field == 0`）のときだけ、従来どおり
  何も作成せず HOME へ戻る（キャンセル）。あわせて、これまで
  `window_load()` で固定文言のまま更新されていなかった
  `s_tset_hint_layer` を `refresh_timer_set_screen()` 内で編集中
  フィールドに応じて動的に切り替えるようにした（分編集中:
  「SEL:秒へ BACK:キャンセル」、秒編集中: 「SEL:確認へ BACK:分へ戻る」）。
- **理由**: BACK ボタンに「一段階戻る／もう戻れないときはキャンセル」
  という、他の階層的な画面遷移で一般的な意味を持たせることで、確認画面
  まで無駄に往復せずに分の値を直せるようにした。ヒントの動的更新は、
  ADR-027 でボタンの意味が変わった際に文言を追従させ忘れていた既存の
  ズレ（「SEL長:決定」という削除済みの長押し確定を指す文言が残っていた）
  も合わせて解消するもの。
- **トレードオフ**: なし。ボタンの意味を1箇所変更し、ヒント文言の同期を
  追加しただけで、他の画面・ロジックへの影響はない。

## ADR-031: タイマーの時間設定で、現在の長さをプリフィルしないようにする

- **日付**: 2026-07-29
- **状態**: 採用
- **事象**: ADR-028 でタイマーの SELECT 長押しを「現在の長さをプリセット
  した分秒ピッカーを開く」方式にしたが、レビューで「リセットして未確定
  のまま HOME に戻り、再度入ると元の状態を覚えている。リセットは文字通り
  リセットなので初期化されている方が分かりやすい」という指摘を受けた。
  ADR-028 は「値を変えずに確定すれば元の長さへのリセットとして機能する」
  ことを狙った設計だったが、「リセット」という言葉から素直に期待される
  「まっさらな初期状態に戻る」という直感とズレがあった。
- **決定**: `slot_select_long_click`（タイマー分岐）で、既存タイマーの
  `duration` をピッカーにプリフィルするのをやめ、新規作成時と同じ
  デフォルト値（`TSET_DEFAULT_MINUTES`=5分, `TSET_DEFAULT_SECONDS`=0秒）
  から常に開始するようにする。この2定数は `menu_item_timer()` の新規
  作成分岐とも共有し、「時間設定を開く」という操作が新規・既存編集
  どちらの入口から入っても同じ初期状態になることを保証する。
- **理由**: 「リセット」を文字通りの初期化として扱う方が、ユーザーが
  期待する挙動と一致し、かつ実装もシンプルになる（前回値を計算して
  引き継ぐロジックが不要になる）。ADR-028 が狙っていた「無変更確定で
  元の長さに戻せる」という利便性は失われるが、そもそも「今の長さを覚えて
  おいて確定するだけ」なら SELECT 短押しでの一時停止/再開で十分に近い
  ことができ、「時間を設定し直す」機能としては常に明示的に値を入力する
  方が一貫性がある。
- **トレードオフ**: 既存タイマーを「元の長さのまま維持したい」だけの
  場合でも、必ず新しい値を（デフォルトの5分0秒から）入力し直す必要が
  あり、値が偶然同じでない限り「無変更で元に戻す」操作はできなくなった
  （そもそも「元の長さ」を保ちたいだけなら SELECT 短押しでの一時停止/
  再開・削除しないという選択で足りるため、実用上の支障は小さいと判断）。

## ADR-032: 「リセット」と「時間の再設定」をボタンごと分離する

- **日付**: 2026-07-29
- **状態**: 採用
- **事象**: ADR-028/ADR-031 で、タイマーの SELECT 長押しを「分秒ピッカー
  （デフォルト値開始）を開く」方式にしていたが、レビューで「リセットが
  中途半端。リセット操作後に戻るボタンで HOME に戻ってから再度タイマーに
  入ると、一時停止中のタイマーが復帰している」という指摘を受けた。
  原因は、SELECT 長押しの時点では実際には何も確定しておらず、ピッカーを
  経由して確認画面で SELECT を押すまでスロットの状態が変わらない設計に
  なっていたため。ユーザーが「リセットした」つもりで BACK によりピッカー
  を抜けると、内部的には何もリセットされておらず、元の（一時停止中などの）
  状態がそのまま残ってしまっていた。
- **決定**: 「リセット」と「時間の再設定」を別ボタンの別操作として明確に
  分離する。
  - **SELECT 長押し = リセット**: 画面遷移せず、その場で即座に確定する
    処理に戻す。`slot_reset()` を ADR-027 の内容（タイマー: Wakeup
    キャンセル + 停止状態 + 元の長さに戻す。SW: 0秒・停止状態・Lap履歴
    クリア）に復元し、`slot_select_long_click` は kind によらず常に
    `slot_reset()` を呼ぶだけのシンプルな実装に戻した。
  - **DOWN = 時間の再設定**（タイマーのみ有効）: 分秒ピッカー
    （`SCREEN_TIMER_SET`、ADR-031 のとおりデフォルト値5分0秒から開始、
    現在の長さはプリフィルしない）を開く。SW では DOWN は従来どおり
    Lap 一覧（`SCREEN_LAPS`）を開く（元々未使用だったタイマー側の DOWN
    に、削除した SELECT長押しの役割を移した形）。
  - `SCREEN_TIMER_CONFIRM` の決定処理（`tconfirm_select_click`）は
    変更なし（`s_open_slot` が既存タイマーを指していれば編集、そうで
    なければ新規作成、という分岐はそのまま有効）。
- **理由**: 「リセット」はボタンを押した瞬間に結果が確定する操作である
  べきで、途中でキャンセル可能な多段階フローに乗せるべきではないと
  判断した。「時間を新しく設定し直す」という別の要求（元のレビュー
  コメント、ADR-028 参照）は、リセットとは独立した操作として引き続き
  提供する。DOWN ボタンはタイマー側で未使用だったため、新しい割り当てに
  ちょうど収まった。
- **トレードオフ**: なし。ボタンの役割を入れ替えただけで、内部状態遷移の
  ロジック（`slot_reset()`/`tconfirm_select_click()`）はいずれも既存の
  実装（ADR-027/ADR-031）をそのまま再利用しており、新しいコードパスは
  増えていない。
